cyberpunk-drone-c2 — candidate future phases
(quick-reference list; full rationale for each lives in NEXT_STEPS.md
under "Known gaps / candidate next steps" — keep both in sync if this
list changes)

1. Single-instance only — DONE, Phase 13 (2026-09-16)
   All three (WebSocket broadcast, simulator tick gate, RateLimiter) now
   coordinate via a shared cluster_state table + DB-backed rate_limit_hits,
   using atomic conditional UPDATEs and request-driven polling - no
   background thread (those reliably die in this hosting env, see Phase 3).
   Verified with two real local server processes sharing one Postgres DB.
   See NEXT_STEPS.md.

2. Per-drone ingestion credentials — DONE, Phase 12 (2026-09-16)
   drones.token_digest + POST .../rotate_token + DELETE .../token. Scoped
   strictly to that drone's telemetry endpoint, never satisfies
   admin_access?. See NEXT_STEPS.md.

3. Rate-limit telemetry ingestion — DONE, Phase 11 (2026-09-16)
   POST /api/drones/:slug/telemetry now throttled to 60 posts/60s per
   drone slug via RateLimiter's new :telemetry bucket. See NEXT_STEPS.md.

4. Admin-configurable alert thresholds — DONE, Phase 14 (2026-09-16)
   alert_rules table + POST/DELETE /api/alert_rules, admin UI panel.
   Also fixed 3 real bugs found while building this: Sequel's
   where(col: [x, nil]) silently drops NULL rows, a Ruby-heredoc escape
   bug that broke the ENTIRE dashboard <script> block's parsing in a real
   browser since Phase 12 (never caught before - see NEXT_STEPS.md), and
   a battery-stream duplicate-chip regression. See NEXT_STEPS.md.

5. Drone-declared stream schema
   Stale-feed detection and chart units only apply after a stream has
   reported at least once - no way to flag "this drone was supposed to
   report vibration and never has." A per-drone manifest (expected stream
   names + units) registered at provisioning time would close that gap.

6. Outbound alert delivery
   Alerts only ever appear inside the dashboard's own panel - nobody is
   notified unless they're looking at the page. A webhook/Slack/email
   push on a *new* alert would close the loop for real operational use.

7. Firmware integrity verification
   POST /api/firmware validates extension and size but not authenticity -
   nothing stops a malicious .bin from being "flashed" if it's under 8MB.
   A required checksum or signature would close that gap.

8. Bulk drone provisioning
   POST /api/drones and GET /drones.csv handle one drone and read-only
   export respectively - no CSV/bulk *import* counterpart for standing up
   a larger fleet at once.
